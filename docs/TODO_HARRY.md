# Что делается руками — пошагово

Здесь то, что может сделать только владелец: ключи и секреты во внешних
панелях. Каждый пункт — по шагам, с проверкой в конце.

Быстрая проверка, что из этого уже сделано (одна команда, ничего не меняет):

```bash
curl -s https://kisy.onrender.com/ready
```

В ответе поле `features`: `turnstile`, `webpush`, `fcm`, `turn`, `blob_s3`.
`false` означает «переменные не заданы, фича не работает». На 29.09.2026 там
`turnstile=false`, `webpush=false`, `turn=false`, `blob_s3=false`.

---

## 0. СРОЧНО: регистрация на проде не работает

**Что происходит.** Любая попытка зарегистрироваться отвечает
`503 CAPTCHA_UNAVAILABLE` («Проверка недоступна, попробуйте через минуту»).
Проверено запросом 29.09.2026. Новые люди зайти не могут вообще; вход
существующих аккаунтов работает.

**Почему.** В production проверка Cloudflare Turnstile включена всегда и
работает fail-closed: нет ключей — регистрация закрывается, а не открывается
ботам. Ключи `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET` в дашборде Render
никогда не задавались (в `render.yaml` они помечены `sync: false`, то есть
их вводит владелец).

### Шаги

1. [dash.cloudflare.com](https://dash.cloudflare.com/) → в меню слева
   **Turnstile** → *Add widget*.
2. Name: `kisy`. Hostnames: добавьте **два** значения —
   `kisy.onrender.com` и `localhost` (второе нужно вебвью
   Android-приложения, оно живёт на `https://localhost`).
   Widget Mode: **Managed**. → *Create*.
3. Cloudflare покажет **Site Key** и **Secret Key**.
4. Render → сервис **kisy** → **Environment**:
   - `TURNSTILE_SITE_KEY` = Site Key,
   - `TURNSTILE_SECRET` = Secret Key.
   → **Save changes**, сервис перезапустится сам.

**Проверка.** Дождитесь **Live** и выполните:

```bash
curl -s https://kisy.onrender.com/ready | grep -o '"turnstile":[a-z]*'
```

Должно быть `"turnstile":true`. После этого откройте страницу регистрации —
появится галочка проверки, и регистрация пройдёт.

## 0.1. Тихо выключенные фичи (не срочно, но знать надо)

Те же `features` показывают ещё три `false`. Ничего не падает — просто
фичи не работают, и раньше об этом нельзя было узнать:

| Поле | Что не работает | Что задать |
|---|---|---|
| `webpush` | Уведомления в браузере (в приложении пуши идут через FCM и работают) | `VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` — **новую** пару (`npx web-push generate-vapid-keys`), старая сожжена; плюс `VAPID_SUBJECT=mailto:kisyandco@gmail.com` |
| `turn` | Звонки через симметричный NAT (мобильный интернет, корпоративный Wi-Fi): не соединяются | `TURN_URLS` + `TURN_SECRET` своего coturn. Без своего сервера — пункт откладывается, звонки в простых сетях работают |
| `blob_s3` | Файлы лежат в Postgres Neon, а не в объектном хранилище: бесплатный лимит базы съедается вложениями | `BLOB_S3_ENDPOINT`, `BLOB_S3_BUCKET`, `BLOB_S3_ACCESS_KEY`, `BLOB_S3_SECRET_KEY` (подойдёт тот же Cloudflare R2, что и для бэкапов, отдельный бакет) |

Важно: задавать **всю** пару или всю четвёрку сразу. Половина теперь роняет
старт с понятным сообщением — это осознанно, чтобы фича не оказалась мёртвой
молча.

## 1. Перевыпустить сервисный ключ Firebase

**Зачем.** Старый ключ (проект `kisy-64c0b`) однажды попал в переписку, то
есть считается раскрытым. Пока он действует, кто угодно с этим файлом может
слать пуши вашим пользователям от имени приложения.

**Что происходит, пока не сделано.** Пуши работают; риск в том, что их может
слать посторонний.

### Шаги

1. Откройте [Firebase Console](https://console.firebase.google.com/) → проект
   **kisy-64c0b** → шестерёнка → **Project settings** → вкладка **Service
   accounts**.
2. Нажмите **Manage service account permissions** — откроется Google Cloud
   Console со списком сервисных аккаунтов.
3. Найдите аккаунт вида `firebase-adminsdk-xxxxx@kisy-64c0b.iam.gserviceaccount.com`
   → вкладка **Keys**.
4. **Сначала создайте новый:** *Add key* → *Create new key* → **JSON** →
   *Create*. Файл скачается сам. Не создавайте его на общем компьютере и не
   пересылайте в мессенджерах.
5. Закодируйте файл в base64 (PowerShell, подставьте свой путь):

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("$HOME\Downloads\kisy-64c0b-firebase-adminsdk.json")) | Set-Clipboard
   ```

   Строка окажется в буфере обмена.
6. Render → сервис **kisy** → **Environment** → переменная
   `FCM_SERVICE_ACCOUNT` → вставьте строку → **Save changes**. Сервис
   перезапустится сам.
7. Дождитесь, пока Render покажет **Live**, и проверьте пуш: попросите кого-то
   написать вам, когда приложение свёрнуто. Уведомление пришло — новый ключ
   работает.
8. **Только теперь удалите старый ключ** в той же вкладке *Keys* (корзина
   напротив старой записи). Если удалить до проверки, пуши отвалятся молча.
9. Удалите скачанный JSON с диска (корзина + очистить корзину).

**Проверка.** Пуш дошёл при свёрнутом приложении, в логах Render нет строк
`fcm: ... 401` или `invalid_grant`.

## 2. Секреты для резервных копий базы

**Зачем.** Ежедневный workflow «DB backup» падает каждое утро больше недели:
у него нет ни пароля для шифрования, ни места, куда класть копию. Сейчас
**резервных копий базы не существует** — при потере данных восстанавливать
будет нечего.

Нужны два секрета: пароль шифрования и приватный бакет (подойдёт Cloudflare
R2 — у него бесплатный объём и S3-совместимый API).

### 2.1. Пароль шифрования

1. Придумайте длинный случайный пароль (20+ знаков) — например, из менеджера
   паролей. Сохраните его там же: **без него копия не расшифруется**, а значит
   бесполезна.
2. GitHub → репозиторий → **Settings** → *Secrets and variables* → **Actions**
   → *New repository secret*:
   - Name: `BACKUP_GPG_PASSPHRASE`
   - Secret: ваш пароль

### 2.2. Бакет Cloudflare R2

1. [dash.cloudflare.com](https://dash.cloudflare.com/) → **R2** → *Create
   bucket*. Имя, например, `kisy-backups`. Регион — автоматический.
   Публичный доступ **не включать**.
2. **R2** → *Manage R2 API Tokens* → *Create API token*:
   - Permissions: **Object Read & Write**
   - Specify bucket: только `kisy-backups`
   - TTL: без срока (или год — тогда поставьте себе напоминание)
3. После создания вы увидите три значения — их показывают один раз:
   **Access Key ID**, **Secret Access Key** и **endpoint** вида
   `https://<account-id>.r2.cloudflarestorage.com`.
4. Добавьте в GitHub четыре секрета (там же, где в 2.1):

   | Name | Значение |
   |---|---|
   | `S3_BUCKET` | `kisy-backups` |
   | `S3_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` |
   | `S3_ACCESS_KEY_ID` | Access Key ID из шага 3 |
   | `S3_SECRET_ACCESS_KEY` | Secret Access Key из шага 3 |

### 2.3. Проверка

1. GitHub → **Actions** → workflow **DB backup** → *Run workflow*.
2. Прогон должен стать зелёным, а в логе — строка о загрузке файла в бакет.
3. Загляните в R2: в бакете лежит файл вида
   `kisy-YYYY-MM-DD-HHMM.sql.gz.gpg`.

**Восстановление** (когда понадобится) описано в
[docs/runbook.md](runbook.md), раздел «Backup / restore».

## 3. Резервная копия ключа подписи приложения

Файл `Documents\kisy-signing\kisy-signing.jks` и его пароли — это **право
обновлять приложение в Google Play**. Потеряете — опубликовать обновление
будет невозможно никогда: только новое приложение с нуля, без пользователей и
отзывов.

1. Скопируйте файл в менеджер паролей (как вложение) или на зашифрованный
   диск, который лежит не там же, где ноутбук.
2. Туда же — пароль хранилища, alias ключа и пароль ключа.
3. Проверьте, что копия открывается: скопируйте её в другую папку и выполните
   `keytool -list -keystore <копия>` — он спросит пароль и покажет отпечаток
   `3a9ef2ae…aa06`.
