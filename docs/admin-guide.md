# KISY — Руководство администратора

Для **CEO** (уровень допуска 1) — единственного аккаунта с неограниченным
доступом. Всё описанное здесь соответствует панели администрирования
(иконка щита) и API `/admin`.

## Два типа аккаунтов

Тип задаётся один раз — в момент регистрации — и потом не меняется.

| | **Обычный** (без приглашения) | **Пригласительный** (по токену) |
|---|---|---|
| Уровень 1–10 | **нет вообще** | есть |
| Рейтинг, условия повышения, голосования, админка | скрыты, и сервер отвечает 403 | как раньше |
| Группы с порогом | не видит | по своему уровню |
| Группы и сообщества без порога | создаёт и видит | тоже |
| Чаты, звонки, заметки, шифрование | есть | есть |
| Лента сообществ | на месте Рейтинга в таб-баре | карточкой в Хабе |

Ключевое, что стоит понять правильно: у обычного аккаунта уровня **нет**, а
не «десятый». Он не внизу иерархии — он вне её, поэтому ни один порог его не
пускает, и выдать ему роль нельзя (сервер ответит 422, а база откажет сама).
Если сотрудник должен попасть в иерархию — его приглашают заново, как нового
человека.

**Найти обычного пользователя можно, но не «полистав список».** Директории
сотрудников у него нет: он ищет только по полному имени, целиком. Это
сознательно — открытая регистрация означает, что аккаунт может завести кто
угодно, а закрытый корпоративный мессенджер не отдаёт такому аккаунту список
всех сотрудников. Писать при этом он может любому, кого нашёл, и ему тоже
может написать любой.

**Выключить открытую регистрацию** на конкретном сервере:
`REGISTRATION_OPEN=false` в окружении. Тогда без токена зарегистрироваться
нельзя, а экран регистрации сразу говорит об этом, не дожидаясь отправки формы.

**Защита от ботов (Cloudflare Turnstile).** Каждая регистрация — и по
приглашению, и без — проходит проверку Turnstile: сервер сверяет токен виджета
с Cloudflare до любых других проверок. Без валидного токена — `403
CAPTCHA_FAILED`, аккаунт не создаётся; если Cloudflare недоступен — `503`,
регистрация закрыта (fail-closed). В production проверку выключить нельзя
(`TURNSTILE_ENABLED=false` там игнорируется); без ключей регистрация отвечает
503, остальное приложение работает.

Настройка:
1. Cloudflare → **Turnstile** → *Add widget*. Режим — **Managed**.
   Hostnames: домен веба (сейчас `kisy.onrender.com`) и **`localhost`** —
   это origin Android-приложения (`https://localhost` в WebView Capacitor).
   Без `localhost` в приложении виджет падает с ошибкой 110200.
2. Скопировать *Site Key* и *Secret Key* в окружение: `TURNSTILE_SITE_KEY`,
   `TURNSTILE_SECRET` (на Render — в дашборде, они `sync: false`).
3. `TURNSTILE_HOSTNAMES` — те же хосты через запятую: токен, выданный на любом
   другом хосте, сервер не примет.

Локально и в тестах проверка по умолчанию выключена; включить можно с
тестовыми ключами Cloudflare (всегда проходят): site
`1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`.

## Модель допуска

Десять уровней: 1 (CEO) — самый сильный … 10 (Гость) — самый слабый.
**Меньший номер означает более высокий допуск.** Видимость направлена
сверху вниз:

- У группы есть **минимальный допуск** (`minRoleLevel`). Она видна только
  пользователям этого уровня или **сильнее**. Более слабые пользователи её
  не видят — причём API возвращает *не найдено*, а не *запрещено*, чтобы
  нельзя было даже узнать о её существовании.
- Более высокий уровень может начать личный чат с равными или более
  слабыми пользователями; слабый пользователь не может инициировать диалог
  «наверх».

## Онбординг пользователя (приглашения)

Приглашение нужно, чтобы дать человеку **уровень**. Зарегистрироваться без
него теперь можно (если `REGISTRATION_OPEN` не выключен), но такой аккаунт
останется вне иерархии — см. «Два типа аккаунтов» выше.

1. Панель администрирования → **Приглашения** → *Создать приглашение*.
2. Скопируйте **токен** или готовую **ссылку регистрации**.
3. Передайте новому сотруднику. Токен действует **ровно 120 секунд** и
   работает **один раз**. Если истёк — создайте новый.

Новый аккаунт создаётся с минимальным допуском (уровень 10). Повысьте его
при необходимости (см. ниже).

## Управление пользователями

Панель администрирования → **Пользователи**:

- **Смена роли** — выберите новый уровень в выпадающем списке. Свою
  собственную роль изменить нельзя (защита от блокировки последнего CEO).
- **Сброс пароля** — задаёт новый пароль; при этом **завершаются все
  сессии пользователя** и на следующем входе требуется сменить пароль.
  Используйте при блокировках или утере доступа.
- **Деактивация / Активация** — деактивация блокирует вход и немедленно
  завершает сессии пользователя. Себя деактивировать нельзя. Аккаунты
  никогда не удаляются, только деактивируются.

## Группы и доски задач

- Любой пользователь может создать группу, но её минимальный допуск **не
  может превышать его собственный** — он должен иметь возможность в ней
  состоять.
- **Удаление группы:** **CEO может удалить любую группу**; в остальных
  случаях группу может удалить только её **основатель**. Удаление сносит
  чат группы, участников и доску задач.
- У каждой группы может быть **доска задач в стиле Trello**. Доску создаёт
  и управляет колонками только основатель; любой участник добавляет и
  перемещает карточки.
- **Добавить участника** напрямую может только владелец группы или CEO.
- **Сообщество** устроено иначе. Посты публикуются от имени сообщества, а не
  редактора. Доска и календарь в нём — только для редакторов (владелец,
  редактор, модератор) и CEO; обычные участники их не видят. Добавить
  человека в сообщество нельзя никому, включая CEO: в него вступают сами.
  Реакция на пост — одна от человека, другая эмодзи заменяет прежнюю.

## Верификация

Панель администрирования → **Верификация**. Найдите пользователя (по логину
или имени) или группу/сообщество (по названию) и нажмите «Выдать» или
«Снять». Рядом с именем появится значок-печать — в профиле, списке чатов,
шапке переписки, списке участников, ленте и заголовке сообщества. Каждое
действие записывается в журнал аудита (`user.verified`, `group.unverified`
и т. д.) с тем, кто и когда его выполнил.

## Модерация сообществ

Панель администрирования → **Сообщества**. Найдите группу или сообщество,
раскройте строку — там активные санкции, история и действия. **Причина
обязательна**: её увидят основатель и редакторы в уведомлении.

- **Варн** — предупреждение. Третье активное предупреждение **автоматически
  удаляет** сообщество. Ошибочное предупреждение можно «Снять» в истории — оно
  перестанет считаться.
- **Мут** на 1 день, 7 дней, 30 дней или бессрочно — посты сообщества пропадают
  из общей ленты, но внутри сообщества публиковать можно. Снимается досрочно
  в истории.
- **Удалить** (с подтверждением) — сообщество исчезает для всех. Во вкладке
  **Удалённые** видно, когда оно будет удалено окончательно; до этого
  (30 дней) его можно **Восстановить** со всеми постами и участниками —
  предупреждений после восстановления останется не больше двух, так что
  следующее снова удалит. Основатель получит уведомление.

Все действия записываются в журнал аудита.

## Журнал аудита

Панель администрирования → **Аудит** (API: `GET /admin/audit`). Каждое
привилегированное действие записывается неизменяемо: входы и неудачные
попытки, блокировки, создание/использование приглашений, регистрации,
смены ролей, сбросы паролей, активация/деактивация, создание/удаление
групп, удаление сообщений и события повторного использования refresh-токена.
Каждая запись содержит актора, цель, хешированный IP, идентификаторы сессии
и запроса, метку времени в UTC. Журнал **нельзя редактировать или
удалять** — база данных отклоняет любую такую попытку.

## О безопасности

- Пароли хешируются Argon2id; система никогда не хранит и не показывает их.
- Пять неудачных входов блокируют аккаунт на 15 минут; также действуют
  ограничения по частоте запросов на один IP.
- Сессии используют HTTPOnly, SameSite=Strict cookie; «выйти со всех
  устройств» отзывает все сессии.

## Резервные копии

Операторы запускают `make backup` (в проде — ночью через cron) для дампа
базы и `make restore` для восстановления. См. `docs/devops.md`.

## Первичная инициализация (bootstrap)

Самый первый аккаунт CEO создаётся из `BOOTSTRAP_CEO_USERNAME` /
`BOOTSTRAP_CEO_PASSWORD` в `.env`, когда база пуста. После первого успешного
запуска удалите эти переменные и смените пароль на экране профиля.

## Потерян пароль CEO

Штатного пути нет и быть не может: сбрасывать пароли умеет только CEO, а
регистрация закрыта инвайтами, которые тоже выдаёт CEO. Bootstrap здесь не
поможет — он отрабатывает лишь на пустой таблице `users` и на живой базе
ничего не делает.

Поэтому восстановление — операторская процедура, для неё нужен доступ к БД:

```bash
DATABASE_URL='postgres://…' go run ./cmd/resetpw -user ceo
```

Утилита сама придумает пароль и напечатает его, снимет блокировку после
неудачных попыток, отзовёт все сессии и потребует сменить пароль при первом
входе (пароль прошёл через терминал — считаем его скомпрометированным).
Свой пароль задаётся флагом `-password '…'`.

Если до базы можно дотянуться только через веб-консоль (Neon, Supabase),
`-hash-only` напечатает готовый `UPDATE`, и подключение к БД не понадобится:

```bash
go run ./cmd/resetpw -user ceo -password '…' -hash-only
```

Блокировка после неудачных попыток снимается сама через 15 минут — если
пароль верный, а вход отдаёт 429, достаточно подождать.
